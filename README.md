# netspeed

Консольная утилита, которая измеряет скорость скачивания. Она делает **10 последовательных** HTTP-запросов к указанному адресу, на каждый дожидается полного тела ответа и печатает среднее время запроса, общий объём данных и скорость.

Только стандартная библиотека Python, сторонних зависимостей нет.

## Запуск

Нужен Python 3.10+ (запускалось на 3.11, 3.12 и 3.13).

```bash
python -m netspeed <URL>
```

Пример (подойдёт любой достаточно тяжёлый файл или картинка):

```bash
python -m netspeed http://ipv4.download.thinkbroadband.com/10MB.zip
```

Пример вывода:

```
URL:                  http://ipv4.download.thinkbroadband.com/10MB.zip
Requests:             10
Total downloaded:     104.86 MB (104857600 bytes)
Total time:           24.335 s
Average request time: 2.433 s
Download speed:       34.47 Mbit/s
```

Файл `10MB.zip` на самом деле весит 10 МиБ (10 485 760 байт), поэтому десять запросов дают 104.86 МБ: объём утилита считает в десятичных мегабайтах.

### Проверка без интернета

Если внешний адрес недоступен, можно поднять локальный сервер.

```bash
# терминал 1: в любой временной папке (не в репозитории)
python -c "open('big.bin', 'wb').write(bytes(50_000_000))"
python -m http.server 8000

# терминал 2: в корне репозитория
python -m netspeed http://127.0.0.1:8000/big.bin
```

Скорость при этом получится нереально высокой: данные не уходят дальше локальной машины.

## Единицы и методика

- **Скорость** выводится в **Мбит/с** (мегабиты в секунду, 1 Мбит = 10⁶ бит), как в тарифах провайдеров.
- Скорость считается как **суммарный объём в битах / суммарное время запросов**, а не как среднее скоростей отдельных запросов. Среднее скоростей искажается, если запросы заметно различаются по времени.
- **Объём** это число байт тела ответа, без заголовков. Выводится в МБ (10⁶ байт) и в байтах.
- **Время запроса** отсчитывается от начала установки соединения до последнего байта тела (`time.perf_counter()`, монотонные часы). Каждый запрос открывает новое соединение, поэтому в замер входят DNS, TCP и TLS.
- Тело читается чанками до конца. Если сервер оборвал ответ раньше, чем заявлено в `Content-Length`, это считается ошибкой.
- Таймаут 30 с действует на каждую операцию сокета, а не на весь запрос целиком.

## Поведение при ошибках

Fail fast: первая же неудача прерывает прогон, а в `stderr` выводится сообщение с номером запроса.

| Код выхода | Когда |
|---|---|
| 0 | всё прошло успешно |
| 1 | ошибка скачивания: сеть, HTTP-статус 4xx/5xx, таймаут, оборванный ответ, схема не `http`/`https` |
| 2 | неверные аргументы командной строки |
| 130 | прервано по Ctrl+C |

Принимаются только `http://` и `https://`: `urllib` по умолчанию умеет открывать и `file://`, а утилите это ни к чему.

## Архитектура

Гексагональная, но без лишнего: три слоя и одна точка сборки.

```
netspeed/
├── constants.py            # все числа, строки и единицы измерения
├── domain.py               # Measurement, BenchmarkReport: чистые расчёты, без I/O
├── ports.py                # порт Downloader и DownloadError
├── use_case.py             # run_benchmark: N последовательных запросов
├── adapters/
│   ├── http_downloader.py  # исходящий адаптер: urllib
│   └── cli.py              # входящий адаптер: argparse и вывод
└── __main__.py             # composition root: связывает порт с адаптером
```

Зависимости направлены внутрь: адаптеры знают о ядре, ядро об адаптерах не знает. Весь код, связанный с соединением, находится в `adapters/http_downloader.py`, и заменить `urllib` на другую библиотеку можно, не трогая остальное.

Последовательность запросов это обычный цикл в `use_case.py`. Он сделан намеренно простым: конкурентность нарушила бы ТЗ и исказила бы замер, потому что запросы делили бы одну полосу пропускания. Вся «взрослость» в том, что цикл живёт в прикладном слое и работает через порт, а не в `main` и не внутри HTTP-кода.

## Допущения и что можно улучшить

- Публичные серверы могут ограничивать частые скачивания: например, Wikimedia отвечает `HTTP 429` уже на третьем запросе из десяти. Тогда утилита останавливается с понятной ошибкой, и нужно выбрать другой адрес.
- Скорость показывает путь до конкретного сервера, а не предел вашего канала: далёкий сервер или перегруженный маршрут дадут меньше, чем близкий.
- Повторные запросы к одному адресу могут отдаваться из кеша CDN или прокси, поэтому скорость может получиться оптимистичнее первой загрузки. Прогревочного запроса нет: по ТЗ ровно 10.
- Осознанно не сделаны, чтобы уложиться в объём задачи: параметр `--count`, статистика (min/max/разброс), JSON-вывод, индикатор прогресса, повторные попытки при сбоях.
- Прокси из окружения (`HTTP_PROXY`, `HTTPS_PROXY`) учитываются стандартным поведением `urllib`.
